####   Границы видимости процессов

**Цель модуля:** Понять механизмы изоляции ресурсов в ядре Linux, изучить основные типы namespaces и системные вызова для работы с ними, а также приобрести практические навыки создания изолированных окружений с помощью `ip netns` и `unshare`.
## ЧАСТЬ 1. Теоретические основы

### 1. Что такое Namespaces (Пространства имен)?

**Namespaces (Пространства имен)** — это фундаментальная фича ядра Linux (появилась и активно развивалась начиная с ядер 2.6.x), которая обеспечивает **изоляцию системных ресурсов** для группы процессов.  

Когда процесс находится в определенном namespace, он «видит» только те системные ресурсы, которые ассоциированы с этим namespace. Для остальных процессов системы его изолированные ресурсы остаются невидимыми или представлены иначе.  

> **Главная идея:** Изоляция не создает виртуализацию оборудования (как KVM или VirtualBox). Ядро остается единым, но оно показывает разным процессам разные «проекции» глобальных системных ресурсов. На базе namespaces и cgroups строятся все современные контейнерные технологии (Docker, Podman, LXC/LXD, containerd, Kubernetes).
### 2. Виды Namespaces и изолируемые ресурсы
В ядре Linux существует 8 основных типов namespaces (7 базовых + `TIME_NS`, появившийся в ядре 5.6). Рассмотрим подробно базовые:

```
+-------------------------------------------------------------------+
|                           Ядро Linux                              |
+-------------+-------------+-------------+-----------+-------------+
|   PID NS    |   NET NS    |   MNT NS    |  IPC NS   |   UTS NS    |
| (Процессы)  |  (Cеть)     | (Файлы/Дис) | (Очереди) | (Имя хоста) |
+-------------+-------------+-------------+-----------+-------------+
|                          USER NS (UID/GID)                        |
+-------------------------------------------------------------------+
|                        CGROUP NS (Cgroups)                        |
+-------------------------------------------------------------------+
```
#### 1. PID Namespace (Process ID)
- **Флаг ядра:** `CLONE_NEWPID`
- **Что изолирует:** Дерево идентификаторов процессов (PID).
- **Особенности:** 
    - Внутри нового PID namespace процессы получают новую нумерацию, начиная с **PID 1** (аналог `init` / `systemd` внутри контейнера).
    - Иерархичность: PID namespaces образуют дерево. Родительский namespace видит процессы дочернего (под своими глобальными PID), но дочерний namespace **не видит** процессы родительского.
    - Если процесс с PID 1 внутри namespace завершается, ядро отправляет сигнал `SIGKILL` всем остальным процессам в этом namespace.

#### 2. NET Namespace (Network)

- **Флаг ядра:** `CLONE_NEWNET`
- **Что изолирует:** Сетевой стек ядра.
- **Особенности:**
    - Каждый NET namespace имеет собственные: сетевые интерфейсы (loopback, eth0, veth), таблицы маршрутизации (routing tables), правила файрвола (iptables/nftables), сокеты и списки прослушиваемых портов (listening ports).
    - Двум процессам в разных NET namespaces можно назначить прослушивание одного и того же TCP-порта (например, `:80`) на одном IP-адресе без конфликта.
#### 3. MNT Namespace (Mount point)

- **Флаг ядра:** `CLONE_NEWMNT`
- **Что изолирует:** Таблицу точек монтирования файловой системы.
- **Особенности:**  
    - Процессы в разных MNT namespaces могут монтировать и размонтировать файловые системы (`mount`/`umount`), не влияя на остальную систему.
    - Позволяет создать уникальное представление файловой системы для контейнера (например, смонтировать изолированный `/proc`, `/tmp` или корень `rootfs`).

#### 4. IPC Namespace (Inter-Process Communication)

- **Флаг ядра:** `CLONE_NEWIPC`
- **Что изолирует:** Средства межпроцессного взаимодействия System V IPC и очереди сообщений POSIX MQ.
- **Особенности:**  
    - Изолирует разделяемую память (Shared Memory, `shmget`), очереди сообщений (`msgget`) и семафоры (`semget`).
    - Процессы в разных IPC namespaces не могут взаимодействовать через разделяемую память, даже если выполняются на одном физическом процессоре.

#### 5. UTS Namespace (UNIX Timesharing System)

- **Флаг ядра:** `CLONE_NEWUTS`
- **Что изолирует:** Имя хоста (Hostname) и доменное имя NIS (Domain name).
- **Особенности:**  
    - Позволяет каждому контейнеру иметь собственное сетевое имя (`hostname`), вызывая системную функцию `sethostname()`, не меняя при этом имя основной ОС.
#### 6. USER Namespace (User & Group IDs)

- **Флаг ядра:** `CLONE_NEWUSER`
- **Что изолирует:** Идентификаторы пользователей (UID) и групп (GID).
- **Особенности:**  
    - Самый мощный с точки зрения безопасности namespace.
    - Позволяет сопоставить (map) обычного непривилегированного пользователя на хосте (например, UID 1000) с суперпользователем `root` (UID 0) внутри namespace.
    - Процесс с UID 0 внутри USER namespace имеет полные права `root` внутри этого окружения, но **не имеет прав root** на управляющем хосте (Rootless-контейнеры).
#### 7. CGROUP Namespace

- **Флаг ядра:** `CLONE_NEWCGROUP`
- **Что изолирует:** Представление структуры контрольных групп (cgroups) через `/proc/self/cgroup` и `/sys/fs/cgroup`.
- **Особенности:**  
    - Скрывает от процесса полную иерархию cgroups системы, показывая только ту часть, которая выделена данному контейнеру.
### 3. Низкоуровневые системные вызовы Linux API

Управление namespaces в Linux выполняется с помощью трех ключевых системных вызовов ядра (syscalls).
#### A. `clone()` — создание процесса с флагами изоляции

Системный вызов `clone()` является расширенной версией классического `fork()`. Он создает новый дочерний процесс, но позволяет через битовую маску флагов указать, какие ресурсы нужно изолировать.
- **Сигнатура (C):**
    ```C
    int clone(int (*fn)(void *), void *stack, int flags, void *arg, ...);
    ```
    
- **Принцип работы:**
    Если в поле `flags` передать один или несколько флагов `CLONE_NEW*` (например, `CLONE_NEWPID | CLONE_NEWNET`), ядро при создании дочернего процесса автоматически создаст новые пространства имен соответствующего типа и поместит новый процесс в них.
#### B. `unshare()` — выход из существующего namespace
Системный вызов `unshare()` позволяет **текущему выбывающему процессу** «отсоединиться» от родительских namespaces и создать новые без порождения дочернего процесса через `clone()`.

- **Сигнатура (C):**
    ```C
    int unshare(int flags);
    ```

- **Принцип работы:**
    Процесс вызывает `unshare(CLONE_NEWNET)`, после чего ядро отключает его от текущего NET namespace и создает для него отдельный, пустой NET namespace.

- **Важное нюанс для PID namespace:** Если процесс вызывает `unshare(CLONE_NEWPID)`, сам вызывающий процесс не перемещается в новый PID namespace (так как его PID не может измениться во время выполнения). В новый PID namespace будут помещаться только его **будущие дочерние процессы**.
#### C. `setns()` — подключение к существующему namespace

Системный вызов `setns()` позволяет текущему процессу присоединиться к уже существующему namespace, созданному другим процессом.
- **Сигнатура (C):**
    ```C
    int setns(int fd, int nstype);
    ```
- **Принцип работы:**
    В Linux каждый namespace представлен в виде специального файла в файловой системе `/proc/[PID]/ns/`.
    
    Процесс открывает такой файл (получая файловый дескриптор `fd`) и передает его в `setns()`. После этого процесс становится частью этого namespace.
    _(Именно так работает команда `docker exec` или `nsenter`, «входя» в запущенный контейнер)._


### 4. Внутреннее устройство: Файловая система `/proc/[PID]/ns`

Вы можете посмотреть, к каким namespaces привязан любой процесс в системе:

```bash
ls -l /proc/$$/ns
```
_(где `$$` — PID текущей оболочки Bash)_

Пример вывода:
```
lrwxrwxrwx 1 root root 0 Sep  4 10:00 cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx 1 root root 0 Sep  4 10:00 ipc -> 'ipc:[4026531839]'
lrwxrwxrwx 1 root root 0 Sep  4 10:00 mnt -> 'mnt:[4026531840]'
lrwxrwxrwx 1 root root 0 Sep  4 10:00 net -> 'net:[4026531841]'
lrwxrwxrwx 1 root root 0 Sep  4 10:00 pid -> 'pid:[4026531836]'
lrwxrwxrwx 1 root root 0 Sep  4 10:00 user -> 'user:[4026531837]'
lrwxrwxrwx 1 root root 0 Sep  4 10:00 uts -> 'uts:[4026531838]'
```

**Как это читать:**

Числа вида `4026531841` — это уникальные идентификаторы (inode) пространств имен в ядре. Если у двух разных процессов inode, например, для `net` совпадают — значит, они находятся в **одном и том же** сетевом пространстве имен. Если различаются — процессы изолированы друг от друга по сети.

## ЧАСТЬ 2. Практические лабораторные работы

> Ниже приведены пошаговые практические задания для закрепления материала. All действия выполняются в терминале Linux с правами суперпользователя (`root` или через `sudo`).

### Лабораторная работа №1. Изоляция сетевого стека с помощью `ip netns`

**Цель:** Создать изолированное сетевое пространство имен, связать его с основным хостом через виртуальную пару интерфейсов (`veth-pair`), настроить IP-адресацию и проверить связность.

#### Схема сети

```
 +-------------------------------------------------------+
 |                     Хост (default ns)                 |
 |                                                       |
 |  [veth-host] (192.168.50.1/24)                        |
 |        |                                              |
 +--------|----------------------------------------------+
          |  <--- Виртуальный кабель (veth pair)
 +--------|----------------------------------------------+
 |        |                                              |
 |  [veth-ns]   (192.168.50.2/24)                        |
 |                                                       |
 |                     Сетевое NS: test_ns               |
 +-------------------------------------------------------+
```
#### Шаг 1.1. Создание нового сетевого namespace

Создадим новое изолированное пространство `test_ns`:

```Bash
sudo ip netns add test_ns
```

Проверим список всех сетевых namespaces в системе:

``` Bash
ip netns list
```

_Вывод:_ Должен отобразиться `test_ns`.
Выполним команду `ip link` внутри созданного namespace, чтобы убедиться в его изоляции:

``` Bash
sudo ip netns exec test_ns ip link
```

_Вывод:_ Вы увидите только интерфейс `lo` (loopback) в состоянии `DOWN`. Интерфейсы хоста (`eth0`, `wlan0` и т.д.) здесь недоступны.
#### Шаг 1.2. Создание виртуального кабеля (veth-пары)

Создадим виртуальный кабель с двумя концами: `veth-host` и `veth-ns`:

``` Bash
sudo ip link add veth-host type veth peer name veth-ns
```

Передадим один конец кабеля (`veth-ns`) в созданное пространство `test_ns`:

``` Bash
sudo ip link set veth-ns netns test_ns
```

Проверим интерфейсы на хосте и внутри `test_ns`:

- **На хосте:** `ip link` покажет только `veth-host`.
- **Внутри `test_ns`:** `sudo ip netns exec test_ns ip link` покажет `lo` и `veth-ns`.

#### Шаг 1.3. Настройка IP-адресов и активация интерфейсов

1. **Активируем интерфейсы и задаем IP на хосте:**
    ``` Bash
    sudo ip link set dev veth-host up
    sudo ip addr add 192.168.50.1/24 dev veth-host
    ```

2. **Активируем интерфейсы и задаем IP внутри `test_ns`:**
    ``` Bash
    sudo ip netns exec test_ns ip link set dev lo up
    sudo ip netns exec test_ns ip link set dev veth-ns up
    sudo ip netns exec test_ns ip addr add 192.168.50.2/24 dev veth-ns
    ```
    
#### Шаг 1.4. Проверка сетевой связности (Ping)

1. **Проверяем ping с хоста в сторону namespace (192.168.50.2):**
    ``` Bash
    ping -c 3 192.168.50.2
    ```
    
2. **Проверяем ping из namespace в сторону хоста (192.168.50.1):**
    ``` Bash
    sudo ip netns exec test_ns ping -c 3 192.168.50.1
    ```

_Результат:_ Пакеты успешно проходят в обе стороны. Вы создали два полностью изолированных сетевых стека, соединенных виртуальным каналом.

### Утилиты для работы с пространствами имён
#### Метод 1. Системная утилита `lsns`
Утилита `lsns` (List Namespaces) входит в стандартный пакет `util-linux`. Она сканирует файловую систему `/proc` и показывает таблицу всех используемых namespaces в системе, их ID (inode), тип, PID первого процесса и команду.
```bash
sudo lsns
```

```plaintext
NS TYPE   NPROCS   PID USER COMMAND
4026531836 pid         3     1 root /sbin/init
4026531840 net         3     1 root /sbin/init
...
4026532297 pid         1  5788 root /bin/bash
4026532298 net         1  5788 root /bin/bash
```

**Как это читать:**

1. Найдите строки, где `PID` **не равен 1**.
2. В примере выше видно, что для `PID 5788` созданы изолированные `pid` (`4026532297`) и `net` (`4026532298`).
3. Поле `NPROCS` показывает, сколько процессов сейчас находится внутри этого конкретного namespace.
##### Фильтрация по конкретному типу:
Если вам нужно найти только изолированные сетевые или PID-пространства:
```bash
sudo lsns -t net
sudo lsns -t pid
```

#### Метод 2. Утилита `ps` с выводом номеров namespaces
Стандартный `ps` умеет выводить номера inode namespaces для каждого процесса в системе.
```bash
ps -eo pid,user,args,netns,pidns | grep -v "grep"
```

Показать все пространства имён (`namespaces`) кроме того в котором находится пользователь
```bash
HOST_NET=$(readlink /proc/1/ns/net)
ps -eo pid,args,netns | grep -v "$HOST_NET"
```

#### Метод 3. Поиск через `/proc` вручную (Скриптом)
Если нужно автоматизировать поиск в Bash-скриптах без утилиты `lsns`, можно сравнить ссылки в `/proc/[PID]/ns/` прямо с `PID 1`.
Скрипт-однострочник для хоста, который выведет все PID и команды процессов, находящихся в не-дефолтных `NET` или `PID` namespaces:
```bash
HOST_PID_NS=$(readlink /proc/1/ns/pid)
HOST_NET_NS=$(readlink /proc/1/ns/net)

for pid in /proc/[0-9]*; do
    p=$(basename $pid)
    [ "$p" -eq 1 ] && continue
    
    cur_pid_ns=$(readlink $pid/ns/pid 2>/dev/null)
    cur_net_ns=$(readlink $pid/ns/net 2>/dev/null)
    
    if [ "$cur_pid_ns" != "$HOST_PID_NS" ] || [ "$cur_net_ns" != "$HOST_NET_NS" ]; then
        echo "Найден изолированный процесс PID $p: $(cat $pid/cmdline | tr '\0' ' ')"
        echo "  -> PID NS: $cur_pid_ns"
        echo "  -> NET NS: $cur_net_ns"
    fi
done
```

#### Метод 4. Проверка через деревья процессов (`pstree`)
Поскольку процесс из `unshare` создается как дочерний для команды `unshare`, вы всегда можете визуально увидеть границы изоляции в дереве процессов хоста:
```bash
pstree -p -a | grep -B 2 -A 2 unshare
```
Вывод сразу покажет связь родительского процесса с изолированным дочерним:
```plaintext
├─sshd(885)───sshd(5386)───bash(5388)───unshare(5787)───bash(5788)
```

### Подключение к пространству имён
Подключение к уже запущенному изолированному окружению — это стандартная задача при отладке контейнеров (именно так работают команды `docker exec` или `kubectl exec`).
В основе этого процесса лежит системный вызов **`setns()`**, а стандартная утилита, которая предоставляет удобный интерфейс для него в командной строке — это **`nsenter`** (от _Namespace Enter_).
В Linux API системный вызов `setns()` переводит вызывающий процесс в указанное пространство имен.

#### Алгоритм работы на уровне ядра:

1. **Открытие дескриптора:** Процесс на хосте открывает специальный файл пространства имен целевого процесса. Эти файлы находятся в виртуальной файловой системе `/proc`:
    - `/proc/[PID]/ns/net` — для Network namespace
    - `/proc/[PID]/ns/pid` — для PID namespace
    - `/proc/[PID]/ns/mnt` — для Mount namespace
    - ...и так далее.

2. **Вызов `setns()`:** Процесс вызывает функцию `setns(int fd, int nstype)` для каждого открытого дескриптора.

3. **Смена окружения:** Ядро проверяет права доступа (требуется `CAP_SYS_ADMIN`, т.е. права root) и переключает контекст исполнения текущего процесса на выбранные пространства имен.

Утилита `nsenter` перехватывает namespaces указанного процесса или файла монтирования и запускает внутри них выбранную программу (по умолчанию — системную оболочку).
Допустим, в первом терминале запущен изолированный `bash` через `unshare`. На хосте (во втором терминале) найдем его PID:
```bash
sudo lsns -t pid
# ИЛИ через ps:
ps aux | grep "[b]ash"
```
Предположим, глобальный PID этого процесса на хосте — **`5788`**.

Чтобы подключиться ко **всем** пространствам имен процесса `5788` и запустить там новый `bash`:
```bash
sudo nsenter --target 5788 --all /bin/bash
```
**Разбор основных флагов `nsenter`:**
- `-t, --target PID` — указывает PID процесса на хосте, к чьим namespaces мы подключаемся.
- `-a, --all` — подключиться абсолютно ко всем пространствам имен target-процесса (`net`, `pid`, `mnt`, `ipc`, `uts`, `user`, `cgroup`).
Иногда требуется подключиться только к определенному ресурсу (например, проверить сеть контейнера, не меняя корневую файловую систему):
- Только к сетевому стеку (`NET`):
```bash
sudo nsenter --target 5788 --net ip a
```
>> (Команда `ip a` выполнится внутри сетевого окружения процесса 5788, показав его интерфейсы, но текущая файловая система и PID останутся от основного пространства имён). процесс изменит только пространство имён для сетевой подсистемы, а остальные пространства имён будут от того пространства, в котором оно запущено.

- Только к файловой системе и точкам монтирования (`MNT`):
```bash 
sudo nsenter --target 5788 --mount /bin/bash
```

- К сети, процессам и монтированию (самый частый набор):
```bash
sudo nsenter --target 5788 --net --pid --mount /bin/bash
```

-Полное подключение к контейнеру. После выполнения `sudo nsenter -t 5788 -a /bin/bash` вы окажетесь внутри нового экземпляра `bash` привязанного к целевому пространству имён.


### Лабораторная работа №2. Изоляция процессов и файловой системы с помощью `unshare`

> **Цель:** Запустить новый экземпляр `bash` в изолированных PID- и Mount-namespaces, примонтировать изолированную файловую систему `/proc` и убедиться, что процесс видит только себя под PID 1.

#### Шаг 2.1. Понимание проблемы разделяемого `/proc`

Утилита `ps aux` считывает информацию о запущенных процессах из виртуальной файловой системы `/proc`. Если мы просто создадим PID namespace, но оставим старое монтирование `/proc` от хоста, команда `ps aux` продолжит показывать все процессы системы.

Поэтому для полной изоляции нам требуется одновременно изолировать и **PID namespace**, и **Mount namespace** (`MNT`).
#### Шаг 2.2. Запуск изолированного bash

Выполните команду `unshare`:

``` Bash
sudo unshare --pid --mount --fork /bin/bash
```

**Разбор флагов команды:**
- `--pid` — создает новый PID namespace.
- `--mount` — создает новый Mount namespace (копия точек монтирования текущего хоста).
- `--fork` — запускает указанную программу (`/bin/bash`) как дочерний процесс от `unshare`. Это необходимо, так как первый процесс в новом PID namespace становится **PID 1**.
- `/bin/bash` — программа, запускаемая внутри нового окружения.
#### Шаг 2.3. Смонтировать изолированный `/proc`

Находясь внутри созданной оболочки `bash`, проверьте текущий PID процесса с помощью переменной среды:

``` Bash
echo $$
```

_Вывод:_ Должна отобразиться цифра **`1`**. Ваша текущая оболочка Bash стала главным процессинговым узлом (init-процессом) в этом пространстве!

Однако, если вы запустите `ps aux` прямо сейчас, вы всё еще увидите процессы хоста. Исправим это, перемонтировав `/proc` для нашего Mount namespace:

``` Bash
mount -t proc proc /proc
```

#### Шаг 2.4. Проверка результатов изоляции

Выполните команду просмотра процессов:

```Bash
ps aux
```

_Пример вывода:_

```
USER         PID %CPU %MEM    VSX    RSS TTY      STAT START   TIME COMMAND
root           1  0.0  0.0  10072   5120 pts/0    S+   11:30   0:00 /bin/bash
root           8  0.0  0.0  10616   3328 pts/0    R+   11:32   0:00 ps aux
```

**Что изменилось:**

1. Процесс `/bin/bash` имеет **PID 1**.
2. В системе "видны" только процессы, запущенные внутри этого `unshare`-сеанса. Процессы хоста полностью скрыты.
3. Команда `ps aux` видит только свою собственную работу и родительский `bash`.

#### Шаг 2.5. Завершение работы и очистка

1. **Выйдите из изолированного bash:**

    ``` Bash
    exit
    ```

    _(При выходе из PID 1 весь изолированный namespace автоматически уничтожается ядром)._

1. **Удалите созданный сетевой namespace `test_ns`:**
    ``` Bash
    sudo ip netns del test_ns
    ```
    _(При удалении `test_ns` связанная пара `veth-ns`/`veth-host` удаляется автоматически)._
