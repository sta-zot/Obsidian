
Разделение между **namespaces** и **cgroups** — это фундамент контейнеризации (Docker, LXC, systemd-nspawn). Простыми словами:
- **Namespaces** дают _изоляцию_ (что процесс **видит**: свои процессы, сеть, точки монтирования).
- **Cgroups (Control Groups)** обеспечивают _ограничение и учёт ресурсов_ (сколько процесс **может взять**: CPU, RAM, I/O).

## Что такое cgroups и зачем они нужны

Без cgroups любой процесс в Linux может утилизировать 100% процессора или забрать всю оперативную память, из-за чего сработает механизм ядра OOM Killer (Out Of Memory) и аварийно завершит random-процессы, включая критически важные службы.

**Cgroups (Control Groups)** — это фича ядра Linux, которая позволяет объединять процессы в иерархические группы и управлять их ресурсами.
### 4 главные функции cgroups:

1. **Ограничение ресурсов (Limiting):** Задать лимит на использование RAM (например, максимум 2 ГБ), ограничить процент CPU или скорость записи на диск.
2. **Приоритезация (Prioritization):** Выделить больше квантов времени CPU или полосы пропускания ввода-вывода одной группе процессов относительно другой.
3. **Учёт (Accounting):** Измерять, сколько ресурсов реально потребляет группа процессов (полезно для мониторинга или биллинга в облаках).
4. **Управление (Control):** Замораживать (freeze/thaw) или останавливать все процессы в группе одной командой.
## Почему именно cgroups v2 (отличия от v1)

Изначальная версия (cgroups v1) появилась в ядре 2.6.24 (2008 год) и имела фундаментальные архитектурные недостатки. В ядре 4.5 (2016) была официально представлена **cgroups v2**, а в современных дистрибутивах (Ubuntu 21.10+, Debian 11+, RHEL 9+) она включена по умолчанию.

|**Параметр**|**cgroups v1**|**cgroups v2**|
|---|---|---|
|**Иерархия**|**Множественная:** Каждая подсистема (cpu, memory, blkio) могла иметь своё независимое дерево групп.|**Единая:** Одно общее дерево для всех ресурсов. Процесс находится в одном узле для всех контроллеров.|
|**Правило потоков**|Процессы и их отдельный threads могли находиться в разных cgroups.|**No Internal Processes:** Процессы находятся только в "листьях" дерева. Промежуточные узлы содержат только группы.|
|**Управление памятью**|Память и I/O отслеживались отдельно (кэш страниц диска не связывался с контроллером I/O).|Память, кэш страниц и буферизованный I/O учитываются совместно.|
|**OOM Killer**|Убивал отдельные процессы внутри cgroup без учёта контекста.|Поддерживает **Group OOM**: возможность завершить _все_ процессы группы целиком при нехватке памяти.|
### Почему v1 была проблемой:

В v1 процесc мог быть в cgroup `cpu:/apps/web`, но при этом находиться в `memory:/system/unlimited`. Это приводило к сложнейшим гонкам блокировок (deadlocks) в ядре и невозможности адекватно ограничить асинхронную запись на диск (буферизованный I/O уходил в обход лимитов).

В **v2** всё подчинено единому дереву. Если группа ограничивается, её CPU, память и I/O контролируются согласованно.

## Подсистемы (Контроллеры) cgroups v2

Управление cgroups v2 происходит через псевдо-файловую систему, обычно смонтированную в `/sys/fs/cgroup`.

В cgroups v2 включение контроллеров происходит сверху вниз по дереву с помощью файлов `cgroup.controllers` (доступные) и `cgroup.subtree_control` (активные для дочерних групп).

Основные контроллеры:
- **`memory`** — контроль оперативной памяти:
    - `memory.max` — жесткий лимит (OOM killer убьет процесс при превышении).
    - `memory.high` — мягкий лимит (ядро начинает агрессивно вытеснять страницу памяти в swap и замедлять процесс).
    - `memory.current` — текущее потребление.
    - `memory.oom.group` — если `1`, при OOM завершаются _все_ процессы в этой cgroup.
- **`cpu`** — контроль процессорного времени
    - `cpu.weight` — пропорциональное распределение (от 1 до 10000, аналог `niceness`).
    - `cpu.max` — абсолютный лимит (например, `200000 100000` означает "максимум 2 ядра на каждые 100мс").
- **`io`** — контроль ввода-вывода (диски)
    - `io.weight` — относительный приоритет I/O.
    - `io.max` — лимит IOPS и BPS (байтов в секунду) для конкретных устройств.
- **`pids`** — защита от fork-бомб:
    - `pids.max` — максимальное количество процессов/потоков внутри группы.
- **`freezer`** — приостановка выполнения
    - `cgroup.freeze` — запись `1` мгновенно останавливает все процессы группы без отправки сигналов SIGSTOP (удобно для создания снапшотов).

## Как cgroups v2 и Namespaces работают вместе

Для создания полноценного контейнера ядро сочетает оба механизма:

```
+-------------------------------------------------------------------+
|                        Linux Kernel                               |
|                                                                   |
|   +-----------------------+           +-----------------------+   |
|   |      NAMESPACES       |           |       CGROUPS V2      |   |
|   |  (Что процесс ВИДИТ)  |           | (Сколько ПОТРЕБЛЯЕТ)  |   |
|   |                       |           |                       |   |
|   |  - pid (свои PID)     |           |  - memory.max = 512M  |   |
|   |  - net (свои сетевые) |  PROCESS  |  - cpu.max = 50000    |   |
|   |  - mnt (свои диски)   |  =======> |  - pids.max = 100     |   |
|   |  - user (свои UID)    |           |                       |   |
|   +-----------------------+           +-----------------------+   |
+-------------------------------------------------------------------+
```

1. **Создание изоляции:** Ядро вызывает системный вызов `clone()` с флагами `CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS...`. Процесс получает изолированный взгляд на систему (Namespace)
2. **Наложение ограничений:** Системный менеджер (systemd или runtime контейнера вроде `runc`) помещает PID этого процесса в нужный узел `/sys/fs/cgroup/docker/<container_id>/cgroup.procs`.
3. **Исполнение:** Процесс считает, что он единственная ОС на сервере (благодаря namespace), но ядро жестко пресекает любые попытки вылезти за 512 МБ RAM или забрать больше 50% CPU (благодаря cgroups v2).
## Практический пример: создаём ограничение вручную

Вы можете протестировать работы cgroups v2 прямо в консоли Linux (нужны права root):

```Bash
# 1. Переходим в директорию cgroups v2
cd /sys/fs/cgroup

# 2. Включаем контроллеры памяти и CPU для дочерних групп
echo "+memory +cpu" > cgroup.subtree_control

# 3. Создаем свою cgroup (просто создав директорию)
mkdir my_limited_group
cd my_limited_group

# 4. Устанавливаем лимит памяти в 100 Мегабайт
echo "104857600" > memory.max

# 5. Переносим текущую оболочку bash в эту группу
echo $$ > cgroup.procs

# 6. Проверяем текущее потребление нашей группы
cat memory.current
```

Если теперь внутри этого bash запускать процессы, съедающие больше 100 МБ памяти, ядро мгновенно вмешаются и завершит их по причине OOM, защитив остальную систему.
