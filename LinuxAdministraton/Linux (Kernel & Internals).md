### [[Модуль 1. Namespaces]]

**Цель:** Понять, как ядро скрывает от процесса глобальные ресурсы системы, создавая иллюзию отдельной ОС.
- **Теоретическая база:**
    - Виды namespaces: `PID` (дерево процессов), `NET` (сетевой стек), `MNT` (точки монтирования), `IPC` (межпроцессное взаимодействие), `UTS` (hostname), `USER` (UID/GID mapping), `CGROUP`.
    - Системные вызовы: `clone()` (создание с флагами изоляции), `unshare()` (выход из существующего namespace), `setns()` (подключение к существующему namespace).
        
- **Практические задания:**
    1. Создать изолированное сетевое пространство с помощью `ip netns add test_ns`. Настроить `veth`-пару (виртуальный кабель), пробросить один конец в `test_ns`, задать IP-адреса и проверить `ping` между пространствами.
    2. Запустить чистый `bash` в новом PID- и Mount-namespace с помощью утилиты `unshare`:
        ```Bash
        sudo unshare --pid --mount --fork /bin/bash
        ```
    3. Внутри созданного bash примонтировать новый `/proc` (`mount -t proc proc /proc`) и убедиться через `ps aux`, что процессу виден только он сам (получит PID 1).

### [[Модуль Модуль 2. cgroups v2 (Ограничение и учет ресурсов)]]

**Цель:** Изучить единую иерархию управления ресурсами процессора, памяти и ввода-вывода (I/O).

- **Теоретическая база:**
    - Отличия cgroups v1 (многодеревенная структура) от cgroups v2 (унифицированное дерево, отсутствие соревнований за ресурсы).
    - Основные контроллеры: `cpu` (shares/quota/period), `memory` (max, high, oom_group, swap), `io` (weight, max/bps/iops), `pids` (лимит количества процессов).
    - Псевдофайловая система `/sys/fs/cgroup/` и принцип интерфейсных файлов (`cgroup.procs`, `memory.max`, `cpu.max`).
- **Практические задания:**
    1. Создать собственную группу ресурсов вручную: `sudo mkdir /sys/fs/cgroup/my_app`.
    2. Ограничить использование оперативной памяти для созданной группы до 100 МБ:
        ```Bash
        echo "104857600" | sudo tee /sys/fs/cgroup/my_app/memory.max
        ```
    3. Поместить текущий процесс `bash` в группу (`echo $$ | sudo tee /sys/fs/cgroup/my_app/cgroup.procs`) и запустить интенсивный выделятель памяти (например, `stress-ng --vm 1 --vm-bytes 200M`). Наблюдать за срабатыванием Kernel OOM Killer через `dmesg -T`.
    4. Ограничить CPU-время процесса до 20% одного ядра через файл `cpu.max` (`20000 100000`).

### Модуль 3. DIY Container (Сборка "Docker" на чистом Bash)

**Цель:** Объединить Namespaces и cgroups v2, чтобы глубоко осознать, что «контейнер» — это просто обычный процесс Linux с ограничениями ядра.

- **Практический мини-проект:**
    1. Скачать и распаковать минимальный RootFS (например, Alpine Linux rootfs) в директорию `/tmp/alpine_root`.
    2. Написать Bash-скрипт `run_container.sh`, который:
        - Создает с помощью `unshare` новые `PID`, `MNT`, `NET`, `UTS` namespaces.
        - Выполняет `chroot` (или `pivot_root`) в директорию `/tmp/alpine_root`.
        - Монтирует `/proc`, `/sys` и `/dev` внутри изолированной среды.
        - Создает cgroup v2 в `/sys/fs/cgroup/demo_container` и привязывает к нему PID запускаемого процесса.
        - Лимитирует оперативную память и количество PIDs (защита от fork-бомбы).
### [Модуль 4. systemd (Юниты, Таймеры, Slices)](LinuxAdministraton/systemd/Systemd)

**Цель:** Научиться профессионально управлять жизненным циклом демонов и ресурсов в дистрибутивах Linux.

- **Теоретическая база:**
    - Архитектура PID 1: обработка сигналов, сматывание зомби-процессов, параллельный запуск служб.
    - Типы юнитов: `.service`, `.socket` (socket activation), `.timer` (замена cron), `.slice` (группировка ресурсов), `.path`, `.target`.
    - Интеграция `systemd` с cgroups v2 (автоматическое создание slices).
- **Практические задания:**
    1. **Юниты и Зависимости:** Написать `.service` юнит для произвольного скрипта. Настроить политики перезапуска (`Restart=on-failure`), лимиты ресурсов непосредственно в юните (`MemoryMax=256M`, `CPUWeight=50`) и зависимости (`After=network-online.target`, `Wants=...`).
    2. **Socket Activation:** Написать сервис, который не висит в памяти постоянно, а запускается `systemd` только при приходе TCP-пакета на определенный порт.
    3. **Systemd Timers:** Заменить cron-задачу на связку `.service` + `.timer`. Выполнить точечное планирование с использованием временных окон (`RandomizedDelaySec=`) и отслеживанием пропущенных запусков (`Persistent=true`).
    4. **Slices:** Изучить вывод `systemd-cgls` и `systemd-cgtop`. Создать кастомный `custom.slice`, ограничить его по CPU/RAM и вложить в него два разных сервиса через `Slice=custom.slice`.

### [Модуль 5. IPC (Inter-Process Communication)](LinuxAdministraton/IPC/Inter-Process%20Communication)

**Цель:** Понимать механизмы, с помощью которых процессы обмениваются данными и синхронизируются внутри ОС.

- **Теоретическая база:**
    - **Signals:** Асинхронные уведомления (`SIGTERM`, `SIGKILL`, `SIGHUP`, `SIGCHLD`). Обработка сигналов процессом.
    - **Pipes & FIFOs:** Безымянные каналы (`|`) и именованные каналы (`mkfifo`).
    - **POSIX / System V IPC:**
        - Shared Memory (`shm_open`, `mmap`): самый быстрый способ обмена данными.
        - Message Queues (`mq_open`).
        - Semaphores / Mutexes: синхронизация доступа к ресурсам.
    - **Unix Domain Sockets (UDS):** Сетеподобный интерфейс (`AF_UNIX`) для эффективного взаимодействия процессов на одной машине (в сравнении с loopback TCP).
        
- **Практические задания:**
    1. **Сигналы:** Написать скрипт/программу, перехватывающую `SIGHUP` (для перечитки конфигурации без перезапуска) и `SIGTERM` (для корректного завершения работы / graceful shutdown).
    2. **Unix Sockets:** Настроить связку Nginx + PHP-FPM или Nginx + Go-приложение через Unix Domain Socket (`/run/app.sock`) вместо TCP-порта (`127.0.0.1:8080`). Измерить разницу в задержках и пропускной способности.
    3. **Диагностика IPC:** Научиться отслеживать открытые каналы и сокеты процессов в системе через `ipcs`, `lsipc`, `lsof -U` и анализатор `/proc/<PID>/net/`.

### Лабораторный чек-лист для проверки знаний

Для подтверждения уровня Middle вы должны уметь без гугла ответить и показать на практике:

- Как найти, какой процесс и почему заполнил лимит cgroup по памяти (`memory.current` vs `memory.stat`).
- Как подключиться утилитой `nsenter` к namespace запущенного Docker-контейнера без использования команды `docker exec`.
- Чем отличается отправка `SIGKILL` от `SIGTERM` для процесса с PID 1 внутри container namespace.
- Как через `systemctl set-property` налету изменить лимит памяти для работающего сервиса.
