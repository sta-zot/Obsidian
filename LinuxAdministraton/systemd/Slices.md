## 3. Слайсы (Slices & Cgroups v2)

### 3.1. Концепция и иерархия cgroups v2
Слайсы (`.slice`) позволяют логически группировать сервисы и настраивать иерархическое распределение ресурсов системы. 
**Slices (Слайсы)** в systemd — это инструмент для логического группирования процессов и управления их ресурсами (CPU, RAM, I/O, PIDs) через контрольные группы ядра Linux
По умолчанию в системе есть три базовых слайса:
- `system.slice` — системные службы 
	>контейнер по умолчанию для всех системных сервисов (SSH, Docker, Nginx, PostgreSQL).
- `user.slice` — пользовательские сессии и процессы.
  >контейнер для пользовательских сессий. Каждому вошедшему пользователю внутри создается отдельный `user-UID.slice` (например, `user-1000.slice`).
- `machine.slice` — виртуальные машины и контейнеры.
  >контейнер для виртуальных машин (KVM/QEMU) и контейнеров (LXC, `systemd-nspawn`).
  
А так же
**`-.slice`** (Root Slice) — корень всего дерева cgroups.

#### Принцип вложенности (Parent-Child)

Иерархия слайсов задается прямо через их имена с использованием дефиса `-`:
- `workload.slice` — родительский слайс.
- `workload-db.slice` — дочерний слайс для БД. Его полный путь в cgroups: `workload.slice/workload-db.slice`.
- `workload-web.slice` — дочерний слайс для веб-серверов.
    
> **Главный закон иерархии cgroups v2:** Лимиты родительского слайса являются абсолютным потолком для всех его дочерних слайсов и сервисов. Дочерний слайс не может получить больше ресурсов, чем выделено родителю.

### 3.2. Анатомия `.slice` файла
Файл слайса располагается в `/etc/systemd/system/` (например, `/etc/systemd/system/apps.slice`) и состоит из двух основных секций: `[Unit]` и `[Slice]`.

```TOML
[Unit]
Description=Application Layer Slice
Documentation=man:systemd.slice(5)

[Slice]
# --- Ограничения по памяти (RAM) ---
MemoryHigh=3G
MemoryMax=4G
MemorySwapMax=1G

# --- Ограничения по процессору (CPU) ---
CPUQuota=200%
CPUWeight=100

# --- Ограничения Ввода/Вывода (Disk I/O) ---
IOWeight=100
IOReadBandwidthMax=/dev/sda 100M
IOWriteBandwidthMax=/dev/sda 50M

# --- Ограничение процессов ---
TasksMax=500
```

### 3.3. Полный справочник атрибутов секции `[Slice]`
Все атрибуты управления ресурсами, доступные в `[Slice]`, также могут применяться напрямую в секции `[Service]`, но вынос их в слайс позволяет управлять группами процессов централизованно.
#### 3.3.1. Память (`Memory`)
Управление RAM в cgroups v2 работает через концепцию мягких и жестких границ, защищая систему от `OOM Killer` (Out Of Memory).

| **Директива**       | **Значение**         | **Описание и поведение**                                                                                                                                                                                                              |
| ------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`MemoryMin`**     | Объём (`500M`, `2G`) | **Гарантированная память.** Ядро Linux никогда не отберет этот объем памяти у слайса в пользу других процессов, даже при сильном дефиците RAM в системе.                                                                              |
| **`MemoryLow`**     | Объём (`1G`)         | **Мягкая защита.** Память слайса будет отбираться (reclaim) в последнюю очередь, только если не останется свободной памяти в других группах.                                                                                          |
| **`MemoryHigh`**    | Объём (`3G`)         | **Мягкий лимит (Throttling).** При превышении этого порога процессы в слайсе **не убиваются**, но замедляются: ядро начинает агрессивно отбирать кэш и выделять новые страницы с задержкой. В journalctl отправляется предупреждение. |
| **`MemoryMax`**     | Объём (`4G`)         | **Жесткий лимит.** Абсолютный потолок. Если процессы внутри слайса превышают `MemoryMax` и не могут освободить память, внутри слайса срабатывает **OOM Killer** и уничтожает один из процессов группы.                                |
| **`MemorySwapMax`** | Объём (`512M`, `0`)  | Максимальный объем подкачки (Swap), который могут использовать процессы слайса. Значение `0` полностью запрещает уйти в Swap.                                                                                                         |
#### 3.3.2. Процессор (`CPU`)

| **Директива**     | **Значение**                                                   | **Описание и поведение**                                                                                                                                                                                                                                                                |
| ----------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`CPUQuota`**    | Проценты (`50%`, `200%`)                                       | **Жесткое ограничение процессорного времени.**<br>• `100%` = ровно 1 ядро процессора.<br>• `200%` = суммарная мощность 2 ядер.<br>• `50%` = пол-ядра.                                                                                                                                   |
| **`CPUWeight`**   | Число от `1` до `10000`<br><br>  <br><br>_(По умолчанию: 100)_ | **Относительный приоритет (CFS Share).** Настраивает пропорцию распределения CPU при **100% загрузке процессора**.<br> _Пример:_ Если `Slice-A` имеет `CPUWeight=200`, а `Slice-B` имеет `CPUWeight=100`, то при конкуренции за процессор Slice-A получит 66% времени, а Slice-B — 33%. |
| **`AllowedCPUs`** | Диапазон ядер (`0,1` или `0-3`)                                | **Привязка к ядрам (CPU Affinity).** Разрешает процессам слайса исполняться только на указанных физических/логических ядрах CPU.                                                                                                                                                        |
#### 3.3.3. Дисковый ввод/вывод (`IO`)

| **Директива**             | **Значение**                                     | **Описание и поведение**                                                                                               |
| ------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| **`IOWeight`**            | Число от `1` до `10000`<br>_(По умолчанию: 100)_ | Относительный приоритет доступа к диску при конкуренции ввода/вывода (работает аналогично `CPUWeight`).                |
| **`IOReadBandwidthMax`**  | `/dev/device speed`                              | Ограничение максимальной скорости **чтения** с конкретного устройства.<br>_Пример:_ `IOReadBandwidthMax=/dev/sda 100M` |
| **`IOWriteBandwidthMax`** | `/dev/device speed`                              | Ограничение максимальной скорости **записи** на конкретное устройство.<br>_Пример:_ `IOWriteBandwidthMax=/dev/sda 20M` |
| **`IOReadIOPSMax`**       | `/dev/device iops`                               | Ограничение максимального количества операций чтения в секунду (IOPS).                                                 |
| **`IOWriteIOPSMax`**      | `/dev/device iops`                               | Ограничение максимального количества операций записи в секунду (IOPS).                                                 |
#### 3.3.4. Ограничение процессов (`Tasks`)

| **Директива**  | **Значение**                     | **Описание**                                                                                                                                                                               |
| -------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`TasksMax`** | Число (`100`, `10%`, `infinity`) | Максимальное количество потоков/процессов (PIDs) внутри слайса. **Отличная защита от Fork-бомб.** Значение в процентах рассчитывается от системного лимита ядра (`sysctl kernel.pid_max`). |
### 3.4. Как привязать Service к Slice
Есть три способа поместить сервис в слайс.
#### Способ 1: Прямое указание в юните (Рекомендуемый)
В файле сервиса (например, `/etc/systemd/system/heavy-worker.service`):

```TOML
[Unit]
Description=Heavy Background Task

[Service]
ExecStart=/usr/local/bin/heavy-worker
# Привязка к созданному слайсу:
Slice=workload.slice
```
#### Способ 2: Через имя слайса (Автоматическая иерархия)
Если назвать юнит-файл слайса `/etc/systemd/system/workload-analytics.slice`, systemd автоматически сделает его дочерним для `workload.slice`.
В сервисе можно указать:

```TOML
[Service]
Slice=workload-analytics.slice
```

> 1. Имя файла `workload-analytics.slice` через дефис говорит systemd: _«Я — дочерний слайс для `workload.slice`»_.
> 2. В файловой системе cgroups v2 автоматически строится иерархия: `/sys/fs/cgroup/workload.slice/workload-analytics.slice/`.

Сервис попадает **ровно туда, куда явно привязан** через директиву `Slice=`. Сервис привязывается именно к тому `.slice`, который указан в его файле конфигурации.
##### Сценарий А. Сервис смотрит напрямую в родительский слайс
Если в файле сервиса `/etc/systemd/system/heavy-worker.service` указать:

```TOML
[Service]
Slice=workload.slice
```
Тогда путь cgroup для процесса будет: `/sys/fs/cgroup/workload.slice/heavy-worker.service` _(Сервис находится на одном уровне с дочерним слайсом `workload-analytics.slice`)._
##### Сценарий Б. Сервис смотрит в дочерний слайс
Чтобы сервис попал именно в дочерний слайс, в `/etc/systemd/system/heavy-worker.service` нужно указать имя **дочернего** слайса:

```TOML
[Service]
Slice=workload-analytics.slice
```
Тогда путь cgroup для процесса станет: `/sys/fs/cgroup/workload.slice/workload-analytics.slice/heavy-worker.service`

######  пример иерархии
Представьте, что у нас есть:
1. `workload.slice` — общие лимиты для всего фонового стека (например, `MemoryMax=10G`).
2. `workload-analytics.slice` — лимиты для аналитики (например, `MemoryMax=4G`, ограничение `CPUQuota=200%`).
3. `workload-reports.slice` — лимиты для генерации отчетов.
Визуально дерево Cgroups в системе будет выглядеть так:

```Plaintext
-.slice (Root cgroup)
 └── workload.slice  <--- [Лимит: 10G RAM] (Родитель)
      │
      ├── workload-analytics.slice  <--- [Лимит: 4G RAM] (Дочерний слайс)
      │    ├── heavy-worker.service    <--- Указал Slice=workload-analytics.slice
      │    └── clickhouse.service      <--- Указал Slice=workload-analytics.slice
      │
      ├── workload-reports.slice    <--- [Лимит: 2G RAM] (Дочерний слайс)
      │    └── pdf-generator.service   <--- Указал Slice=workload-reports.slice
      │
      └── standalone-script.service    <--- Указал Slice=workload.slice напрямую
```

#### Способ 3: Динамическая привязка на лету
Запуск произвольной команды в изолированном слайсе без создания файлов на диске:

```Bash
systemd-run --slice=custom.slice --property=MemoryMax=500M /usr/bin/python3 script.py
```



#### Совокупность лимитов в иерархии cgroups v2
> Лимит родительского слайса действует **совокупно** на всю ветку (на сам родительский слайс + на все его дочерние слайсы и сервисы вместе взятые).

В cgroups v2 действует строгая иерархия:
- **`workload.slice` (`MemoryMax=10G`)**: Это суммарный потолок для всей ветки. Сумма оперативной памяти, занятая `standalone-script.service` + `heavy-worker.service` + `clickhouse.service` + `pdf-generator.service`, **никогда не может превысить 10 ГБ**.
- **`workload-analytics.slice` (`MemoryMax=4G`)**: Это локальный потолок для дочерней группы. `heavy-worker.service` + `clickhouse.service` вместе не могут занять более 4 ГБ.

#### Что произойдёт если сервис из дочернего "Слайса" запросит память но в родительском не хватает.

**Исходные данные:**
1. `workload.slice`  выделено 10GB
2. `workload-analytics.slice`  4GB
3. `standalone-script.service` (напрямую в `workload.slice`) уже использует **9 ГБ**.
4. `heavy-worker.service` (внутри `workload-analytics.slice`) пытается выделить **3 ГБ**.
**Ход событий в ядре Linux:**

5. **Проверка локального лимита (`workload-analytics.slice`):**
    Процессу `heavy-worker.service` нужно 3 ГБ. Локальный лимит слайса равен 4 ГБ. Проверка успешна ($3\text{ ГБ} \le 4\text{ ГБ}$).
6. **Проверка родительского лимита (`workload.slice`):**
	Ядро поднимается выше по дереву cgroups и считает общую память всей ветки:
    $$\text{Текущее потребление (9 ГБ)} + \text{Запрос (3 ГБ)} = 12\text{ ГБ}$$
    Сумма 12 ГБ **превышает** родительский лимит `MemoryMax=10G`.
7. **Реакция ядра (Reclaim & OOM Killer):**
	- **Шаг 1 (Попытка очистки):** Ядро приостанавливает выделение памяти и пытается освободить 2 ГБ (сбрасывает дисковый кэш/page cache) внутри ВСЕЙ ветки `workload.slice`.
    - **Шаг 2 (OOM Killer):** Если память освободить не удалось, срабатывает **Out-Of-Memory (OOM) Killer**. Он выбирает и принудительно завершает (`SIGKILL`) один из процессов **внутри ветки `workload.slice`**, чтобы вернуть потребление всей группы в рамки 10 ГБ.
#### Кого убьёт OOM Killer в этой ситуации?
OOM Killer выбирает жертву на основе показателя `oom_score` (чем больше процессов и занимаемой ими памяти в группе, тем выше шанс попасть под удар).
- **С наивысшей вероятностью будет убит процесс из `standalone-script.service`**, так как он заграбастал 90% лимита всей родительской группы (9 ГБ из 10 ГБ).
- После уничтожения процесса с 9 ГБ общая память ветки резко упадет, родительский лимит освободится, и `heavy-worker.service` успешно получит свои 3 ГБ.
#### Как защитить важные процессы от такой конкуренции?

Чтобы процессы из дочернего слайса не страдали из-за «прожорливых» соседей из родительского слайса, используйте гарантированное резервирование памяти в `[Slice]`:
###### Директивы защиты памяти:
- **`MemoryMin=2G`** (внутри `workload-analytics.slice`):
        **Абсолютная гарантия.** Ядро зарезервирует 2 ГБ строго под этот слайс. Родительский `workload.slice` физически не сможет отдать процессы `standalone-script.service` более 8 ГБ ($10\text{ ГБ} - 2\text{ ГБ}$), даже если дочерний слайс в данный момент эти 2 ГБ не использует.
- **`MemoryLow=2G`** (внутри `workload-analytics.slice`):
        **Мягкая защита.** При нехватке памяти в родительской группе ядро начнет забирать память и натравливать OOM Killer в первую очередь на те процессы, которые превышают свои пороги `MemoryLow`, защищая `workload-analytics.slice`.
### 3.5. Мониторинг и диагностика слайсов

#### 1. Интерактивный мониторинг ресурсов (Аналог `htop` для cgroups)
Показывает CPU, RAM, I/O и количество PIDs по каждому слайсу и сервису в реальном времени:

```bash
systemd-cgtop
```
#### 2. Просмотр дерева Cgroups
Показывает структуру дерева процессов:

```bash
systemd-cgls
```

#### 3. Инспекция текущих лимитов конкретного слайса

```Bash
systemctl show workload.slice
```

#### 4. Динамическое изменение лимитов без перезапуска (On-the-fly)
Вы можете изменить параметры слайса прямо в рантайме. Изменения применятся мгновенно и сохранятся на диске в виде drop-in файла:

```Bash
sudo systemctl set-property workload.slice MemoryMax=8G CPUQuota=300%
```

### Полный практический сценарий
Предположим, у вас на сервере одновременно работают СУБД и фоновые скрипты обработки видео. Вы хотите гарантировать, что скрипты обработки не заберут всю память и не уронят СУБД.

1. **Создаем `/etc/systemd/system/background-processing.slice`:**

```TOML
[Unit]
Description=Slice for background heavy tasks
Documentation=https://wiki.internal/ops/cgroups

[Slice]
# Не даем забрать более 4 ГБ ОЗУ и блокируем уход в Swap
MemoryMax=4G
MemorySwapMax=0

# Даем не более 2 ядер CPU
CPUQuota=200%

# Понижаем приоритет CPU и I/O относительно СУБД
CPUWeight=20
IOWeight=20

# Защита от утечки PIDs
TasksMax=200
```

2. **Активируем конфигурацию:**

```Bash
sudo systemctl daemon-reload
```

3. **Прописываем `Slice=background-processing.slice` в файле `/etc/systemd/system/video-converter.service`.**
4. **Проверяем распределение:**

```Bash
systemd-cgtop
```

Ещё один пример изолированного слайса для тяжелых или фоновых задач `/etc/systemd/system/workload.slice`:

```TOML
[Unit]
Description=High-Load Background Services Slice
Documentation=man:systemd.slice(5)

[Slice]
# Ограничение по оперативной памяти:
MemoryHigh=4G
MemoryMax=6G
MemorySwapMax=512M

# Ограничение процессора (50% = 0.5 ядра, 100% = 1 ядро, 200% = 2 ядра):
CPUQuota=50%

# Приоритет CPU в cgroups (1-10000, по умолчанию 100):
CPUWeight=50
# Ограничение ввода/вывода на конкретный диск:
IOReadBandwidthMax=/dev/sda 50M
IOWriteBandwidthMax=/dev/sda 20M
```

> Пояснение к RAM: `MemoryHigh` запускает механизмы очистки страниц памятью (throttling), а при достижении `MemoryMax` срабатывает `OOM Killer` внутри слайса.
