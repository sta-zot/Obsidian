**Socket Activation** — это одна из самых мощных архитектурных возможностей systemd, унаследованная от macOS `launchd` и развивающая идеи классического `inetd`.
Главная идея: **systemd открывает и слушает сетевой сокет (или UNIX socket) от имени сервиса**, а сам процесс сервиса запускает только тогда, когда на этот сокет приходит первый входящий пакет или запрос.
## 1. Архитектура и преимущество перед классической схемой
### Классический запуск (без Socket Activation):
1. systemd запускает `nginx.service`.
2. Nginx инициализирует память, читает конфиги, создаёт socket, вызывая `bind()` и `listen()` на порту `80`.
3. Все остальные сервисы, которым нужен Nginx, вынуждены ждать через `After=nginx.service` полное завершение инициализации.
### Запуск через Socket Activation:
1. systemd мгновенно создаёт сокет (вызывает `socket()`, `bind()`, `listen()`) на порту `80`.
2. systemd **сразу считает сокет готовым** и запускает все зависимые сервисы параллельно.
3. Если запрос пришёл до того, как демон стартовал, ядро Linux помещает входящее соединение в **SYN backlog queue** (очередь ожидания).
4. systemd запускает `.service` и передаёт ему **уже готовый открытый файловый дескриптор (File Descriptor)**.
### Что это даёт:
- **Запуск по требованию (On-Demand / Lazy Loading):** Сервис не висит в RAM, пока к нему никто не обращается (идеально для редких задач, микросервисов, локальных демонов).
- **Параллельная загрузка без race conditions:** Убирается необходимость настраивать сложную очередность запуска — сокеты доступны с первой секунды.
- **Zero-Downtime обновления и устойчивость к падениям:** Если главный процесс сервиса упал или перезапускается (`systemctl restart`), сокет остается открытым в ядре. Клиенты не получают ошибку `Connection Refused`, их запросы просто подмораживаются на доли секунды в очереди ядра.
## 2. Связка файлов: `.socket` + `.service`
Socket activation работает через пару файлов с одинаковым именем: `myapp.socket` и `myapp.service`.
### 1. Файл сокета: `/etc/systemd/system/myapp.socket`

Конфигурационный файл `.socket` определяет параметры сокетов, каналов (FIFOs) или сетевых портов, которые `systemd` слушаeт от имени сервиса.
Файл сокета состоит из трех основных секций: **`[Unit]`**, **`[Socket]`** (специфичные параметры сокета) и **`[Install]`**.
## 1. Секция `[Socket]`: Адресация и Типы Сокетов
Секция `[Socket]` определяет, _какой именно_ сокет создается. В одном `.socket` файле можно указывать несколько директив `Listen*` одновременно (например, слушать IPv4 и IPv6 одновременно).
### 1.1. Директивы прослушивания (`Listen...`)

| **Директива**                 | **Формат значения**                                                 | **Описание**                                                                                            |
| ----------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **`ListenStream=`**           | `8080`, <br>`127.0.0.1:8080`,<br> `[::1]:8080`,<br> `/run/app.sock` | Создает поток данных (TCP или UNIX domain stream socket). Аналог `SOCK_STREAM`.                         |
| **`ListenDatagram=`**         | `9000`,<br>`127.0.0.1:9000`,<br>`/run/app-dgram.sock`               | Создает датаграммный сокет (UDP или UNIX domain datagram socket). Аналог `SOCK_DGRAM`.                  |
| **`ListenSequentialPacket=`** | `/run/app-seq.sock`                                                 | Создает сокет последовательных пакетов (UNIX domain sequential packet socket). Аналог `SOCK_SEQPACKET`. |
| **`ListenFIFO=`**             | `/run/app.fifo`                                                     | Создает именованный канал (FIFO Pipe) в файловой системе.                                               |
| **`ListenSpecial=`**          | `/dev/ttyS0`                                                        | Открывает специальный символный файл устройства или файл из `/proc` / `/sys`.                           |
| **`ListenNetlink=`**          | `netlink_family buffer_size`                                        | Открывает сокет ядра Netlink (например, `kobject_uevent 65536` для событий железа).                     |
| **`ListenMessageQueue=`**     | `/queue_name`                                                       | Открывает очередь сообщений POSIX (POSIX Message Queue).                                                |
| **`ListenUSBFunction=`**      | `/sys/kernel/config/usb/...`                                        | Слушает endpoints USB-гаджета (USB FunctionFS).                                                         |

## 2. Секция `[Socket]`: Управление поведением и активацией

| **Директива**                                                     | **Допустимые значения**              | **Описание**                                                                                                                                                                                                                                                                                                |
| ----------------------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`Accept=`**                                                     | `no` _(по умолчанию)_ / `yes`        | **Главный параметр режима:**<br>• `no`: systemd передает один слушающий сокет единому экземпляру сервиса (`app.service`). Сервис сам делает `accept()`.<br>• `yes`: systemd сам вызывает `accept()` на каждое подключение и запускает отдельный процесс `app@.service` под каждого клиента (режим `inetd`). |
| **`ExecStartPre=`**                                               | Команда с аргументами                | Команда, исполняемая **до** того, как сокет будет создан и привязан (bind).                                                                                                                                                                                                                                 |
| **`ExecStartPost=`**                                              | Команда с аргументами                | Команда, исполняемая **сразу после** того, как сокет успешно создан и привязан.                                                                                                                                                                                                                             |
| **`ExecStopPre=`**                                                | Команда с аргументами                | Команда, исполняемая **до** закрытия сокета.                                                                                                                                                                                                                                                                |
| **`ExecStopPost=`**                                               | Команда с аргументами                | Команда, исполняемая **после** того, как сокет закрыт и освобожден.                                                                                                                                                                                                                                         |
| **`Service=`**                                                    | Имя юнита (`custom.service`)         | Имя активации. Указывается только если имя `.service` файла отличается от имени `.socket` файла.                                                                                                                                                                                                            |
| **`MaxConnections=`**                                             | Число (`64`)                         | Максимальное количество одновременных подключений при `Accept=yes`. Достигнув лимита, новые подключения отклоняются.                                                                                                                                                                                        |
| **`MaxConnectionsPerSource=`**                                    | Число (`10`)                         | Максимальное количество одновременных подключений **с одного IP-адреса** при `Accept=yes`.                                                                                                                                                                                                                  |
| **`TriggerLimitIntervalSec=`**<br>---<br>**`TriggerLimitBurst=`** | Время (`2s`)<br>---<br>Число (`200`) | Ограничение частоты активаций сервиса.<br>Если за время указанное в `TriggerLimitIntervalSec` приходит больше подключений чем указано в `TriggerLimitBurst` , сокет временно приостанавливается.                                                                                                            |
## 3. Секция `[Socket]`: Права доступа и Файловая Система (UNIX Sockets / FIFOs)

Эти параметры применяются, если сокет создает файл в файловой системе (`/run/...` или `/tmp/...`):

| **Директива**        | **Значение**                        | **Описание**                                                                                 |
| -------------------- | ----------------------------------- | -------------------------------------------------------------------------------------------- |
| **`SocketUser=`**    | Имя пользователя / UID              | Пользователь-владелец файла сокета в FS. _(Не влияет на сетевые TCP/UDP порты)._             |
| **`SocketGroup=`**   | Имя группы / GID                    | Группа-владелец файла сокета в FS.                                                           |
| **`SocketMode=`**    | Восьмеричное число (`0660`, `0666`) | Права доступа POSIX на файл сокета.                                                          |
| **`DirectoryMode=`** | Восьмеричное число (`0755`)         | Права доступа на родительские директории, если systemd создает их автоматически.             |
| **`RemoveOnStop=`**  | `true` / `false`                    | Удалять ли файл сокета из FS при остановке сокета (`systemctl stop`). По умолчанию `false`.  |
| **`Symlinks=`**      | Пути через пробел                   | Создает дополнительные симлинки на файл сокета (например, `Symlinks=/run/mysql/mysql.sock`). |
## 4. Секция `[Socket]`: Сетевые параметры ядра (Socket Options)
Параметры тонкой настройки TCP/IP стека ядра Linux:

| **Директива**               | **Значение**                              | **Описание**                                                                                                                 |
| --------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **`Backlog=`**              | Число (`128`, `4096`)                     | Размер очереди необработанных соединений (`listen(fd, backlog)`). По умолчанию берется системный `SOMAXCONN`.                |
| **`BindIPv6Only=`**         | `default`, `both`, `ipv6-only`            | Управляет `IPV6_V6ONLY`. Запрещает или разрешает принимать IPv4 подключения на IPv6 сокете.                                  |
| **`KeepAlive=`**            | `true` / `false`                          | Включает отправку TCP Keep-Alive пакетов для проверки живых соединений.                                                      |
| **`KeepAliveTimeSec=`**     | Время (`7200s`)                           | Пауза бездействия перед отправкой первого Keep-Alive пакета.                                                                 |
| **`KeepAliveIntervalSec=`** | Время (`75s`)                             | Интервал между повторными отправками Keep-Alive проверок.                                                                    |
| **`KeepAliveProbes=`**      | Число (`9`)                               | Количество безответных Keep-Alive проверок, после которого соединение разрывается.                                           |
| **`NoDelay=`**              | `true` / `false`                          | Включает `TCP_NODELAY` (отключает алгоритм Нагла для уменьшения задержек/latency).                                           |
| **`FreeBind=`**             | `true` / `false`                          | Включает `IP_FREEBIND`. Позволяет привязать сокет к IP-адресу, которого **еще нет** на сетевых интерфейсах системы.          |
| **`Transparent=`**          | `true` / `false`                          | Включает `IP_TRANSPARENT`. Позволяет сокету перехватывать трафик, предназначенный другим IP (используется для TPROXY/Proxy). |
| **`ReusePort=`**            | `true` / `false`                          | Включает `SO_REUSEPORT`. Позволяет нескольким процессам биндиться на один и тот же порт.                                     |
| **`ReceiveBuffer=`**        | Объём (`1M`, `64K`)                       | Настраивает размер буфера приема ядра `SO_RCVBUF`.                                                                           |
| **`SendBuffer=`**           | Объём (`1M`, `64K`)                       | Настраивает размер буфера отправки ядра `SO_SNDBUF`.                                                                         |
| **`IPTOS=`**                | Число / Метка (`low-delay`, `throughput`) | Настраивает поле Type of Service (QoS) в заголовке IP-пакетов.                                                               |

## 5. Секции `[Unit]` и `[Install]` в `.socket` файлах

### Секция `[Unit]`

Использует стандартные директивы (`Description`, `Documentation`, `Before`, `After`, `Wants`, `Requires`).
- Обычная практика: сокет заводится до таргета сокетов: `Before=sockets.target`.
### Секция `[Install]`
Определяет поведение при `systemctl enable`:

| **Директива**   | **Значение**     | **Описание**                                                |
| --------------- | ---------------- | ----------------------------------------------------------- |
| **`WantedBy=`** | `sockets.target` | Основной таргет для включения сокетов при загрузке системы. |

```TOML
[Unit]
Description=Socket for My Custom Application
Documentation=https://docs.internal/app

[Socket]
# Слушать на TCP-порту (IPv4 и IPv6)
ListenStream=8080

# ИЛИ слушать на UNIX domain socket
# ListenStream=/run/myapp/myapp.sock

# ИЛИ слушать на UDP-порту
# ListenDatagram=9000

# Права доступа на UNIX socket файл
# В случае с TCP/UDP сокетами игнорируются
SocketUser=www-data
SocketGroup=www-data
SocketMode=0660

# Ограничение очереди входящих соединений (SOMAXCONN)
Backlog=128

[Install]
WantedBy=sockets.target
```
В случае с TCP директивы `SocketUser=` / `SocketGroup=` в файле `.socket` просто **игнорируются** ядром, так как у сетевых портов нет представления в файловой системе
Права на TCP-сокет определяются ядром на этапе его bind/listen:
1. **Бинд порта (`< 1024`):** Сокет создаётся процессом `systemd` (который работает от имени `root`). Поэтому порт `80` или `443` успешно биндится в ядре, несмотря на то, что сам сервис позже запустится под непривилегированным пользователем `appuser`.
2. **Передача дескриптора:** systemd открывает файловый дескриптор и передаёт его процессу `appuser` при старте через наследование FD.
3. **Чтение/Запись:** Для TCP-сокетов ядро Linux проверяет права доступа (`User`/`Group`) **только в момент вызова `bind()`**. Так как `bind()` выполнил `systemd` (root), сам процесс `appuser` спокойно вызывает `accept()`, `read()` и `write()` на уже переданном готовом дескрипторе.

В случае с UNIX Domain Sockets (`ListenStream=/run/myapp/myapp.sock`)
Вот здесь несоответствие пользователей в файле .socet и .service станет **критичной проблемой**.
UNIX-сокет — это специальный файл в файловой системе. На него распространяются стандартные права доступа POSIX (`rwxrwxrwx`):
- При создании файлового сокета systemd устанавливает на файл права из `SocketUser`, `SocketGroup` и `SocketMode` (например, `owner: www-data`, `mode: 0660`).
- Если процесс сервиса запускается под пользователем `appuser` (не входящим в группу `www-data`), он **не сможет открыть файл сокета или получить к нему доступ на чтение/запись**, если сокет создается или пере открывается в FS.

## Полный эталонный пример production-сокета
`/etc/systemd/system/api-gateway.socket`:
```TOML
[Unit]
Description=High-Performance API Gateway Socket
Documentation=https://docs.internal/api/gateway
Before=sockets.target

[Socket]
# Слушаем UNIX socket и TCP порт одновременно
ListenStream=/run/api-gateway/gateway.sock
ListenStream=0.0.0.0:8443

# Права на файл сокета
SocketUser=www-data
SocketGroup=www-data
SocketMode=0660

# Настройки сети и производительности
Backlog=2048
NoDelay=true
KeepAlive=true
ReusePort=true
FreeBind=true

# Режим единого мультипоточного демона
Accept=no

# Защита от спама активаций
TriggerLimitIntervalSec=1s
TriggerLimitBurst=500

[Install]
WantedBy=sockets.target
```
### 2. Файл сервиса: `/etc/systemd/system/myapp.service`

```TOML
[Unit]
Description=My Custom Application Service
Requires=myapp.socket
After=myapp.socket

[Service]
Type=notify
User=appuser
ExecStart=/opt/myapp/bin/myapp

# Безопасность
ProtectSystem=strict
PrivateTmp=true
```

> **Важно:** Секция `[Install]` в `.service` файле не нужна, так как сервис будет активироваться сокетом, а не запускаться при загрузке системы. При старте системы включен (`systemctl enable --now`) должен быть именно `myapp.socket`.
## 3. Как приложение получает файловые дескрипторы
Когда systemd запускает `.service`, он передаёт ему открытые файловые дескрипторы сокетов через стандартный протокол `sd_listen_sockets`.
### Правила передачи FD (File Descriptors):

1. **Количество сокетов:** systemd передает число сокетов в переменной окружения `LISTEN_FDS`.
2. **PID процесса:** Переменная `LISTEN_PID` содержит PID процесса, которому предназначены сокеты (защита от утечки в дочерние процессы).
3. **Нумерация дескрипторов:** Дескрипторы передаются начиная с фиксированного номера **`3`** (так как `0` = stdin, `1` = stdout, `2` = stderr).
    - Второй сокет будет иметь FD = `4`, третий FD = `5` и т.д.
### Пример реализации на Go

Написанное на Go приложение может легко принимать дескрипторы сокетов без самостоятельного вызова `net.Listen()`:
```go
package main

import (
	"fmt"
	"net"
	"net/http"
	"os"
	"strconv"
)

func main() {
	var listener net.Listener

	// Проверяем, передан ли сокет от systemd
	listenFds := os.Getenv("LISTEN_FDS")
	if listenFds != "" {
		count, err := strconv.Atoi(listenFds)
		if err == nil && count > 0 {
			// Открываем файловый дескриптор 3 (первый переданный сокет)
			file := os.NewFile(3, "systemd-socket")
			l, err := net.FileListener(file)
			if err != nil {
				panic(err)
			}
			file.Close() // Закрываем дубликат файлового объекта
			listener = l
			fmt.Println("Успешно запущен через systemd Socket Activation (FD 3)")
		}
	}

	// Фолбэк для локальной разработки (без systemd)
	if listener == nil {
		l, err := net.Listen("tcp", ":8080")
		if err != nil {
			panic(err)
		}
		listener = l
		fmt.Println("Запушен в автономном режиме на :8080")
	}

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "Hello from Socket Activated App!")
	})

	http.Serve(listener, nil)
}
```

## 4. Режимы работы сокетов (`Accept=`)

Параметр `Accept=` в секции `[Socket]` определяет, кто обрабатывает установку входящих соединений (`accept()`):
### 1. `Accept=no` (По умолчанию — рекомендуемый режим для серверов)
- systemd слушает сокет и передает сервис-демону **сам слушающий сокет (Listening socket)**.
- Запускается **один экземпляр сервиса**, который сам принимает все входящие соединения (`accept()`) и обрабатывает их в мультипоточном/асинхронном режиме.
- Работает с стандартным `myapp.service`.
### 2. `Accept=yes` (Режим inetd — один процесс на каждый запрос)
- systemd сам вызывает `accept()` при каждом входящем подключении и передаёт процессу **уже установленное соединение (Connected socket)** прямо в `stdin`/`stdout` (FD `0` и `1`).
- Для каждого клиента спавнится **отдельный процесс** юнита `myapp@.service` (шаблонизированный сервис).
- **Применение:** Старые UNIX-утилиты, SSH-подключения, сервисы с тяжелой изоляцией клиентов.
```TOML
# /etc/systemd/system/echo.socket
[Socket]
ListenStream=7000
Accept=yes

# /etc/systemd/system/echo@.service
[Service]
ExecStart=/usr/local/bin/echo-service
StandardInput=socket
```
## 5. Мониторинг и управление сокетами

```Bash
# Включить и запустить сокет
sudo systemctl enable --now myapp.socket

# Посмотреть статус сокета и количество входящих подключений
systemctl status myapp.socket

# Список всех сокетов в системе, их адресов и активируемых сервисов
systemctl list-sockets

# Проверить, активен ли связанный сервис (должен быть inactive до первого запроса)
systemctl status myapp.service
```
### Пример вывода `systemctl list-sockets`:

```Plaintext
LISTEN                 UNIT         ACTIVATES
/run/dbus/system_bus_socket dbus.socket  dbus.service
[::]:8080              myapp.socket myapp.service
```
