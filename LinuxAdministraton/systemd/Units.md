## 1. Юниты (Service Units)

Юнит — это базовый объект управления в systemd. Все юниты описываются текстовыми декларативными конфигурационными файлами (юнит-файлами).
### Где хранятся юниты:

- `/lib/systemd/system/` или `/usr/lib/systemd/system/` — файлы, поставляемые пакетами дистрибутива (не редактируйте их вручную).
- `/etc/systemd/system/` — пользовательские и администраторские юниты (имеют наивысший приоритет и переопределяют файлы из `/lib/systemd/system/`).
- `~/.config/systemd/user/` — юниты, запускаемые от имени обычного пользователя (без root-прав).
### Анатомия `.service` файла
Создадим шаблон промышленного сервиса `/etc/systemd/system/myapp.service`:

```TOML
[Unit]
Description=My Go Application Service
Documentation=https://docs.example.com/myapp
# Зависимости запуска:
After=network-online.target remote-fs.target target.target
Wants=network-online.target
# Жесткая зависимость (если postgresql упадет/не запустится, наш сервис не запустится):
Requires=postgresql.service

[Service]
Type=notify
User=appuser
Group=appuser
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/bin/myapp --config /etc/myapp/config.yaml
ExecReload=/bin/kill -HUP $MAINPID

# Безопасность и изоляция (Hardening):
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/log/myapp /var/lib/myapp
NoNewPrivileges=true
PrivateTmp=true

# Политика перезапуска:
Restart=on-failure
RestartSec=5s
StartLimitIntervalSec=60s
StartLimitBurst=3

[Install]
WantedBy=multi-user.target
```

### В systemd юниты описываются в формате INI-файлов и делятся на три главных секции (блока):

1. **`[Unit]`** — метаданные, порядок запуска, зависимости и условия выполнения.
2. **`[Service]`** — логика выполнения процесса, типы запуска, безопасность и поведение при сбоях.
3. **`[Install]`** — связи с таргетами (уровнями запуска) при создании симлинков через `systemctl enable`.
### 1.1. Секция `[Unit]`

Секция описывает общий контекст юнита. Она не зависит от того, задействован ли сервис, сокет или таймер.

| Директива           | Назначение и допустимые значения    | Описание и примеров применения                                                                                                                                                                                        |
| ------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`Description`**   | Текст                               | Краткое человекочитаемое описание службы. Отображается в `systemctl status` и логах.                                                                                                                                  |
| **`Documentation`** | URI (`http://`, `https://`, `man:`) | Ссылки на документацию. Выводятся в `systemctl status`.                                                                                                                                                               |
| **`Wants`**         | Имена юнитов через пробел           | **Мягкая зависимость.** Сообщает systemd: «При запуске этого юнита попробуй также запустить указанные». Если они не закроются с ошибкой — сервис всё равно запустится.                                                |
| **`Requires`**      | Имена юнитов через пробел           | **Жёсткая зависимость.** Если указанные юниты не могут быть запущены или упадут, этот юнит мгновенно завершится с ошибкой или не стартует вовсе.                                                                      |
| **`Requisite`**     | Имена юнитов через пробел           | Улучшенный `Requires`. Если указанный юнит **уже** не запущен в момент старта, данный юнит сразу завершится с ошибкой (без попытки их запустить).                                                                     |
| **`BindsTo`**       | Имена юнитов через пробел           | Жесточайшая привязка жизненного цикла. Если юнит из `BindsTo` останавливается или падает, данный юнит **немедленно отключается**. Полезно при привязке сервисов к конкретному железу (например, сетевым интерфейсам). |
| **`After`**         | Имена юнитов через пробел           | **Порядок запуска.** Определяет, что данный юнит должен стартовать строго **после** указанных. *Не задаёт зависимость запуска (для этого нужны `Wants`/`Requires`).*                                                  |
| **`Before`**        | Имена юнитов через пробел           | **Порядок запуска.** Гарантирует, что данный юнит полностью запустится **до** старта указанных юнитов.                                                                                                                |
| **`Conflicts`**     | Имена юнитов через пробел           | **Взаимное исключение.** При старте этого юнита указанные в `Conflicts` службы будут автоматически остановлены.                                                                                                       |
|                     |                                     |                                                                                                                                                                                                                       |
> *(например, `AssertPathExists`)* | Путь к файлу / значению | **Жесткое утверждение.** Аналогично `Condition`, но если проверка не проходит — запуск фейлится с ошибкой. |

### 1.2. Секция `[Service]`
Сердце сервиса. Определяет, как именно запускать процесс, под какими правами и как реагировать на его аварии.
#### 1.2.1. Управление запуском и типами процессов

##### `Type=` (Тип выполнения)
Определяет, как systemd определяет готовность сервиса и отслеживает его PID:
* **`simple`** *(по умолчанию, если есть `ExecStart`)*: systemd считает сервис запущенным сразу после выполнения `execve()`. Не ждёт инициализации.
* **`exec`**: Похож на `simple`, но systemd гарантированно ждёт завершения вызова бинарника (убеждается, что файл существует, имеет права на исполнение и загружен в память).
* **`forking`**: Для классических UNIX-демонов, вызывающих `fork()`. Основной процесс завершается, оставляя дочерний фоновый процесс. Требует указания `PIDFile=`.
* **`oneshot`**: Для однократных задач (скриптов). systemd ждёт полного завершения процесса перед тем, как переходить к следующим юнитам. Часто сочетается с `RemainAfterExit=yes`.
* **`dbus`**: Юнит считается готовым, когда запрашивает имя на шине D-Bus (требует `BusName=`).
* **`notify`**: Идеальный режим. Процесс сам отправляет сигнал `READY=1` в сокет systemd через `sd_notify()`, когда полностью готов принимать трафик/запросы.
#### Директивы исполняемых команд:

```toml
[Service]
ExecStartPre=/usr/bin/check-config.sh
ExecStart=/usr/bin/myapp --config /etc/myapp.conf
ExecStartPost=/usr/bin/send-telemetry.sh
ExecReload=/bin/kill -HUP $MAINPID
ExecStop=/usr/bin/myapp-shutdown.sh
ExecStopPost=/bin/rm -f /tmp/myapp.sock

```

* **`ExecStart`**: Главная команда запуска. Если `Type=oneshot`, можно указывать несколько команд подставляя их последовательно.
* **`ExecStartPre` / `ExecStartPost**`: Команды до и после исполнения основного процесса. Если команда из `ExecStartPre` возвращает не нулевой код — `ExecStart` не вызывается.
* **`ExecReload`**: Команда для перезагрузки конфигурации без остановки процесса (например, отправка `SIGHUP`).
* **`ExecStop` / `ExecStopPost**`: Команды для корректной остановки и последующей очистки ресурсов.

> **Синтаксис команд:**
> * Префикс `-` (например, `ExecStartPre=-/bin/rm ...`) указывает systemd **игнорировать ошибки** этой команды и продолжать запуск.
> * Префикс `@` передает первый аргумент как `argv[0]`.

#### 1.2.2. Управление окружением и правами доступа

| Директива              | Значение                           | Описание                                                                                             |
| ---------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **`User`**             | Имя пользователя / UID             | Пользователь, от имени которого будет запущен процесс. По умолчанию — `root`.                        |
| **`Group`**            | Имя группы / GID                   | Группа процесса.                                                                                     |
| **`WorkingDirectory`** | Путь к директории                  | Рабочая директория процесса (`cd` перед стартом).                                                    |
| **`Environment`**      | `"KEY1=val1" "KEY2=val2"`          | Переменные окружения прямо в файле.                                                                  |
| **`EnvironmentFile`**  | `/path/to/env-file`                | Путь к файлу с переменными (формат `KEY=VALUE`). Префикс `-` отключит ошибку, если файл отсутствует. |
| **`UMask`**            | Восьмеричное число (напр., `0027`) | Маска создания файлов для процесса.                                                                  |

#### 1.2.3. Безопасность и изоляция (Hardening)

Критически важный блок для изоляции демонов от остальной системы:

```toml
[Service]
# Запрещает процессу и его дочерним элементам получать новые привилегии через setuid/setgid
NoNewPrivileges=true

# Делает /usr, /boot и /etc доступными ТОЛЬКО для чтения для этого процесса
ProtectSystem=strict

# Скрывает /home, /root и /run/user от процесса
ProtectHome=true

# Разрешает запись ТОЛЬКО в явным образом указанные директории (если ProtectSystem=strict)
ReadWritePaths=/var/log/myapp /var/lib/myapp

# Мое изолированное временное пространство в /tmp и /var/tmp (недоступно другим процессам)
PrivateTmp=true

# Изоляция сетевого пространства или доступ к конкретным семействам сокетов
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX

# Запрет доступа к реальному железу (/dev)
PrivateDevices=true

# Ограничение доступных системных вызовов (seccomp)
SystemCallFilter=@default @basic-io @file-system ~@clock

```

#### 1.2.4. Политика перезапуска и тайм-ауты

| Директива     | Допустимые значения                                                   | Описание                          |
| ------------- | --------------------------------------------------------------------- | --------------------------------- |
| **`Restart`** | `no`, `always`, `on-success`, `on-failure`, `on-abnormal`, `on-abort` | Условие перезапуска процесса.<br> |
|               |                                                                       |                                   |
• `on-failure` — перезапуск, если код завершения != 0 или был убит сигналом (OOM/Segfault).
• `always` — перезапуск всегда, даже при чистом выходе. |
| **`RestartSec`** | Время (`5s`, `100ms`, `1m`) | Пауза перед автоматическим перезапуском процесса. |
| **`StartLimitIntervalSec`** | Время (`60s`) | Интервал отслеживания частоты перезапусков. |
| **`StartLimitBurst`** | Число (`5`) | Максимальное количество попыток перезапуска за интервал `StartLimitIntervalSec`. Если лимит превышен — systemd переведёт юнит в статус `failed` и прекратит попытки. |
| **`TimeoutStartSec`** | Время (`30s`, `infinity`) | Тайм-аут ожидания старта. Если процесс не поднялся за это время — он убивается. |
| **`TimeoutStopSec`** | Время (`15s`) | Время, которое systemd дает процессу на корректное завершение (`SIGTERM`) перед отправкой жесткого `SIGKILL`. |

### 1.3. Секция `[Install]`
Определяет поведение юнита при выполнении команд `systemctl enable` и `systemctl disable`. Секция игнорируется при обычном вызове `systemctl start`.

| Директива | Значение | Описание |
| --- | --- | --- |
| **`WantedBy`** | Имя таргета (`multi-user.target`, `graphical.target`) | При выполнении `systemctl enable` создает симлинк в директории `.wants` указанного таргета. Служба будет автоматически запускаться при загрузке системы на этом уровне. |
| **`RequiredBy`** | Имя таргета | Создает жесткую привязку в директории `.requires` указанного таргета. |
| **`Alias`** | Альтернативное имя (`myapp-alias.service`) | Позволяет обращаться к сервису по дополнительному имени после включения. |

### Итоговый образцовый Service Unit

Сведём всё в целостную конфигурацию веб-сервиса на Go/Python:

```toml
[Unit]
Description=Production API Gateway
Documentation=https://wiki.internal/services/api-gateway
After=network-online.target postgresql.service
Wants=network-online.target
Requires=postgresql.service

[Service]
Type=notify
User=www-data
Group=www-data
WorkingDirectory=/opt/api-gateway

ExecStartPre=/opt/api-gateway/bin/gateway --check-config
ExecStart=/opt/api-gateway/bin/gateway --env=prod
ExecReload=/bin/kill -HUP $MAINPID

# Изоляция и безопасность
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/log/api-gateway
PrivateTmp=true
NoNewPrivileges=true

# Перезапуск
Restart=on-failure
RestartSec=3s
StartLimitIntervalSec=30s
StartLimitBurst=3

[Install]
WantedBy=multi-user.target

```

### 1.4. Практическое переопределение (Override)

Никогда не копируйте полный файл юнита из `/lib/` в `/etc/`, если нужно изменить 1-2 параметра. Используйте механизмы drop-in файлов:
  
```Bash
# Откроет текстовый редактор и создаст директорию /etc/systemd/system/myapp.service.d/override.conf
sudo systemctl edit myapp.service
```

Внутри файла укажите только изменяемые секции:

```toml
[Service]
Environment="LOG_LEVEL=debug"
ExecStart=
ExecStart=/opt/myapp/bin/myapp --config /etc/myapp/debug.yaml
```

_(Пустой `ExecStart=` обязателен при переопределении команд запуска, чтобы сбросить предыдущее значение)._
